Small Lisp, Spécification
Langage Lisp minimal, interprété (tree-walking), pensé pour du scripting IO simple.

1. Types
Type	Notation	Rust interne
string	"..." (échappement \n, \t, etc.)	String
raw string	'...' (aucun échappement)	String
bool	t / f	bool
integer	[+-]?0[xbo]?N, décimal, 0x hex, 0b binaire, 0o octal	i64
float	N.N	f64
null	_	unit / None
array	[e1 e2 ...], hétérogène, imbricable	Vec<Value>
struct	{k1:v1 k2:v2 ...}, clés identifiants uniquement	Vec<(String, Value)> (ordre d'insertion préservé)
* Les indices de tableau sont 1-based : arr[1] est le premier élément et arr[-1] le dernier.
* Les sélections de tableau sont inclusives : arr[start..end], avec une borne omise
  autorisée (arr[..end], arr[start..]), et arr[[i j]] sélectionne plusieurs éléments.
* Les sélections retournent une nouvelle valeur array.
* Les chaînes utilisent la même indexation 1-based, les indices négatifs et les tranches
  inclusives : str[1] retourne un string, str[start..end] retourne un string, et
  str[[i j]] retourne un array de strings. Les positions sont des graphèmes Unicode
  (pas des octets ni des scalaires Unicode).
* Virgules optionnelles dans [] et {} : traitées comme du whitespace si présentes.
* Vérité (truthiness) : tout est vrai sauf 0 (integer), 0.0 (float), f, _.

2. Identifiants
Regex : [A-Za-z0-9_-]+, ASCII uniquement. Un identifiant ne peut pas commencer par un chiffre en pratique, le lexer doit essayer de parser un nombre en premier ; si ça échoue, il retombe sur un identifiant.
Les symboles `t`, `f`, `_`, `NaN`, `+NaN`, `Inf`, `+Inf` et `-Inf` sont des littéraux réservés et ne peuvent pas être utilisés comme noms de liaison.

2.1 Mots-clés et noms intégrés
* Le lexer ne produit pas de token spécial pour les mots-clés : ils sont lexés comme des
  symboles puis reconnus lorsqu'ils apparaissent en tête d'un appel.
* Les formes spéciales sont : `let`, `set`, `if`, `fn`, `loop`, `break`, `continue`, `match`,
  `and`, `or`, `not`, `expect`, `use`, `eval` et `repl`. Elles contrôlent l'évaluation de leurs
  arguments ; leurs arguments ne sont donc pas nécessairement tous évalués avant l'appel. `eval`
  est décrit en §16, `repl` en §20.
* Les builtins stricts sont : `add`, `sub`, `mul`, `div`, `mod`, `pow`, `eq`, `ne`, `lt`, `gt`,
  `le`, `ge`, `bit-and`, `bit-or`, `bit-xor`, `bit-not`, `bit-shl` et `bit-shr`. Leurs
  arguments sont évalués puis l'opération est appliquée selon les règles d'arité de §6 et de
  typage de §8–§10.
* Le builtin d'interaction est `$`, qui effectue l'interpolation décrite en §14 et inclut la
  correspondance regex via `%~` (moteur et captures décrits en §15). Le module natif `io`
  expose `io.open`, `io.read`, `io.write` et `io.close` après `(use "io")` ; le module natif
  `http` expose `http.get`, `http.post`, `http.put`, `http.patch`, `http.delete` et
  `http.head` après `(use "http")`, décrits en §13.1.
* Les noms de formes spéciales, de builtins stricts et d'interaction ci-dessus sont réservés :
  ni un `let` ni un paramètre de fonction ne peut les utiliser comme identifiant (erreur), de
  sorte qu'un nom ne désigne jamais à la fois une valeur et une forme. Les littéraux réservés
  (`t`, `f`, `_`, `NaN`, `Inf`, `+Inf`, `-Inf`, `+NaN`, `-NaN`) restent interdits en position
  d'identifiant comme avant.
* Ces noms sont reconnus par leur orthographe exacte lorsqu'ils sont en tête d'un appel.
  Une liaison portant le même nom ne remplace donc pas ce builtin dans cette position. Les
  noms peuvent toutefois être utilisés comme noms de liaison dans les autres contextes,
  sous réserve des littéraux réservés ci-dessus.
* Les opérations `io.open`, `io.read`, `io.write` et `io.close` sont des champs du module
  natif `io`, et suivent la représentation des descripteurs appelables.
* `use "str"` charge statiquement un module natif par string. Dans `use nom`, l'expression
  `nom` est évaluée normalement puis sa valeur string sert à la recherche dynamique du module ;
  un symbole `str` non lié produit donc NameError. La forme `(use (let nom valeur))` définit
  immédiatement un module Lisp nommé `nom`. Le registre natif actuel fournit `str`
  (`str.upper`, `str.lower`), `io` et `http`.
* `use` lie `nom` dans le scope courant exactement comme `let` : un nom déjà lié dans CE même
  scope produit DuplicateBindingError et n'est jamais réécrit — seul `set` (§4) modifie une
  liaison existante. L'ombre portée d'une liaison parent reste autorisée.
* Tout membre appelable d'un module doit être un descripteur `{_: callable spec: ...}`.
  `spec` doit contenir `documentation` (string), `arity` (integer), `type` (array, ou `_`
  lorsque `arity` vaut zéro) et `return` (array ou `_`). `type` est une signature unique : un
  tableau d'exactement `arity` entrées, liées positionnellement aux paramètres. Chaque entrée
  est soit un nom de type unique, soit un tableau non vide de noms de type : dans ce cas,
  l'argument est accepté s'il correspond à l'un des types alternatifs, indépendamment des
  autres arguments (les combinaisons autorisées sont le produit cartésien des ensembles — il ne
  s'agit en aucun cas de surcharge/alternatives par signature complète ; `arity` reste un
  entier fixe unique et la longueur de `type` doit toujours égaler `arity`). Le vocabulaire des
  noms de type est `null`, `bool`, `int`, `float`, `string`, `array`, `struct`, `function`,
  `ref` et `any`. L'entrée spéciale `"any"` accepte tout type d'argument, seule ou dans un
  ensemble alternatif (où elle domine l'ensemble). Un nom inconnu et un ensemble vide sont
  refusés dès l'enregistrement du module (jamais une déclaration silencieuse qui ne peut
  matcher) ; `return` est déclaratif uniquement (forme validée, jamais appliquée à la valeur
  retournée). Ces champs sont validés dès l'enregistrement du module et `arity`/`type` sont
  également appliqués à chaque appel.
  Un module natif est une struct ordinaire ; ses membres appelables utilisent un champ `_`
  et un champ `spec`, comme les descripteurs Lisp.
* Seule une struct qui est un descripteur complet (champ `_` et champ `spec`) est appelable :
  l'appel déroule la valeur de `_` — validée appelable — en exactement un niveau et applique
  `spec`. Un champ `_` seul ne rend jamais une struct appelable et n'est jamais déroulé ; il
  n'existe donc pas de chaînes ni de cycles de `_`.

3. Grammaire
form        := call | block | array | struct | literal | field-access | ref
call        := "(" symbol form* ")"
block       := "(" form* ")"                      ; nouveau scope, retourne la dernière valeur
array       := "[" form* "]"
struct      := "{" (identifier ":" form)* "}"
field-access:= identifier ("." identifier)*        ; sucre pour (. (. a b) c)
ref        := "^" postfix-access                  ; référence/alias vers un emplacement
postfix-access := field-access ("[" selector "]")*

* () est le seul constructeur de scope. if/match n'ouvrent un scope que si leur branche est elle-même un ().
* . est l'unique forme d'accès à un champ struct. Les tableaux utilisent exclusivement les crochets : arr[1], arr[-1], arr[2..5], arr[[1 3]].
* . retourne la valeur courante (accès par valeur) : un instantané immuable partagé en lecture et
  isolé en écriture (modèle de valeurs, voir §7). ^ retourne une référence/alias vers l'emplacement
  (variable, champ de struct, élément de tableau) : un emplacement logique (cellule racine +
  chemin), résolu contre la valeur courante à chaque lecture/écriture, voir §7.

4. let / set
* Les deux évaluent strictement leur expression valeur.
* let crée une nouvelle liaison dans le scope courant — le () englobant le plus proche, ou le
  scope de haut niveau du programme. Si le nom est déjà lié dans CE même scope lexical, erreur
  DuplicateBindingError : pas de re-liaison silencieuse. L'ombre portée (shadowing) d'une liaison
  d'un scope parent reste autorisée.
* set modifie une liaison existante, en remontant la chaîne de scopes jusqu'à la trouver ; il ne
  crée jamais de nouvelle liaison. Erreur NameError si le nom n'existe nulle part.
* Lire une variable déréférence toute référence qu'elle contient (§7) : `let` lie donc la valeur
  courante de l'emplacement, pas l'emplacement. `(let q p)` copie la VALEUR courante de p (liaison
  isolée) ; `(let q (^ p))` lie un second alias vivant du même emplacement. `set` à travers un
  alias mute l'emplacement cible (§7).

5. Scopes
* Seul () introduit un nouveau scope lexical ; le haut niveau du programme est lui aussi un scope.
* loop : un seul scope créé à l'entrée, réutilisé à chaque itération (pas de nouveau scope par
  tour), nécessaire pour que (set x (sub x 1)) accumule d'un tour à l'autre. Conséquence : un
  (let ...) rejoué à chaque tour dans le corps du loop est un doublon (DuplicateBindingError).
  Pour lier de nouvelles variables à chaque tour, ouvrir un () dans le corps.
* fn : chaque appel crée un nouveau scope où les paramètres sont liés ; ce scope a pour parent le scope lexical où le fn a été défini (lexical scoping, pas dynamique).
* Les closures capturent l'environnement par référence : set depuis une closure mute bien la variable extérieure. C'est ce qui permet la récursion (le nom se résout au moment de l'appel, pas de la définition) et les compteurs mutables.

6. Fonctions
* L'arité est une propriété de chaque appelable. Les fonctions créées par `fn` ont une arité
  fixe : trop peu ou trop d'arguments → ArityError à l'appel. Les builtins peuvent être fixes
  ou variadiques selon leur définition.
* `add` et `mul` acceptent zéro argument (identités 0 et 1) et un nombre quelconque d'arguments.
  `sub` et `div` acceptent au moins un argument et effectuent un pliage gauche ; `sub` unaire
  est la négation et `div` unaire est le réciproque (Float).
* `eq`, `ne`, `lt`, `gt`, `le` et `ge` acceptent zéro argument ou plus. `eq` et les
  comparaisons d'ordre sont chaînées ; `ne` vérifie que toutes les valeurs sont distinctes
  ; avec zéro ou un argument, le résultat est vrai.
* `mod` et `pow` exigent exactement deux arguments. `bit-and`, `bit-or` et `bit-xor` sont
  variadiques (identités -1, 0 et 0) ; `bit-not` exige exactement un argument. `bit-shl` et
  `bit-shr` exigent exactement deux arguments.
* Il n'y a pas de currying automatique.
* Passage d'argument par valeur par défaut : le paramètre reçoit la valeur courante (instantané
  immuable partagé en lecture, isolé en écriture, §7). Passer ^x fait de l'argument un alias de x
  (le même emplacement logique) : un set dans le corps de la fonction mute la variable de
  l'appelant ; lire le paramètre le déréférence vers la valeur courante.
* Récursion native : le corps d'un fn n'est évalué qu'à l'appel, et la closure référence son environnement par pointeur, pas besoin de letrec.
* Profondeur d'appel bornée : la récursion est limitée à 2048 appels imbriqués (`MAX_CALL_DEPTH`).
  Au-delà, l'évaluateur lève `RecursionError: call depth limit (2048) exceeded …` — une erreur de
  langage ordinaire, positionnée sur l'appel fautif (`fichier:ligne:col` + caret) et accompagnée
  de la pile d'appel vivante (les 40 cadres les plus internes puis « … N more frame(s) omitted »),
  jamais un crash silencieux. L'interpréteur tourne sur un thread à grande pile explicite
  (256 Mo, voir main()) pour que la garde — et non la pile native — borne la récursion ; la
  valeur 2048 est calibrée sur la consommation mesurée (des dizaines de Ko de pile native par
  appel en build debug). Pour une itération sans borne de profondeur, utiliser `loop`.

(let incr (fn (n) (set n (add n 1))))
(let x 5)
(incr ^x)   ; x devient 6 (référence)
(incr x)    ; copie locale incrémentée, x reste 6

7. Références (^)
* ^identifier, ^struct.champ, ^arr[i], ou ^arr (le tableau entier) produisent un alias vers l'emplacement correspondant.
  Les sélections multiples (`^arr[[i j]]`) et les tranches (`^arr[start..end]`) ne peuvent pas
  être des cibles de référence.
* ^ sur un tableau entier est autorisé et permet la mutation en place dans une fonction, l'array passé par référence pointe vers la même structure sous-jacente que celle de l'appelant, toute mutation via des opérations sur ce paramètre (ajout, modification d'un élément, etc.) est visible côté appelant.
* Usages : argument de fonction (mutation explicite, §6), ou liaison locale d'alias :
(let user {name:"Yvan"})
(let n (^ user.name))
(set n "Nouveau")
(use "io")
(io.write 1 ($ "%s" user.name))   ; "Nouveau"

(let nums [1 2 3])
(let push-zero (fn (a) (set a[1] 0)))
(push-zero ^nums)
(io.write 1 ($ "%d" nums[1]))      ; 0 (mutation en place du tableau)
* eq déréférence transparemment : comparer une référence à une valeur compare les valeurs pointées, pas des adresses (le langage n'expose aucune notion d'identité de pointeur ailleurs).
* Modèle de valeurs : les arrays et structs sont des instantanés immuables partagés en lecture.
  Toute lecture (accès par valeur, argument, let) renvoie la valeur courante sans offrir de vue
  mutable ; une mutation ne fait que remplacer l'instantané dans la cellule racine (set, §4). Une
  référence `^` est un EMPLACEMENT logique — cellule racine + chemin de champs/éléments — jamais
  une valeur ni un instantané : elle est résolue contre la valeur COURANTE à chaque lecture et
  chaque écriture.
* Ré-lier la racine déplace l'alias vers la nouvelle valeur : `(let a [1 2]) (let p (^ a[1]))
  (set a [5 6])` → p vaut 5. Si le remplacement rend le chemin invalide (type incompatible :
  array remplacée par une struct, champ remplacé par un scalaire, etc.), la résolution échoue
  déterministiquement avec une erreur de type (« indexing requires an array » / « struct field
  access requires a struct ») — jamais une donnée obsolète, jamais un repli sur l'ancienne
  valeur. Le même alias fonctionne de nouveau dès que l'emplacement redevient valide.
* Lire une liaison contenant une référence déréférence : `(let q p)` copie la VALEUR courante de
  p (liaison complètement isolée, §4) ; seul `(let q (^ p))` crée un second alias vivant sur le
  même emplacement (chaînage à deux sauts). De même, un paramètre reçu par valeur est
  déréférencé à la lecture ; pour muter la cible depuis une fonction, passer `^` (§6).
* Une référence stockée dans un composite (champ de struct, élément de tableau) reste vivante
  pour les lectures : lire le champ / l'élément déréférence la valeur courante. En revanche,
  ÉCRIRE sur la position terminale qui contient une référence REMPLACE la référence elle-même
  (sémantique feuille) : `(set box.p 7)` met 7 dans box.p, la cible de l'ancienne référence n'est
  pas mutée. Une variable détenant une référence, et tout pas intermédiaire d'un chemin, s'écrivent
  À TRAVERS (write-through) : avec `a[1] = (^ b)`, `(set a[1][2] 9)` mute b.
* Cycles : assigner une valeur contenant une référence qui pointe — directement ou indirectement,
  y compris via une chaîne d'alias écrite à travers un appel de fonction — vers un ancêtre de
  l'emplacement cible crée un cycle ; l'assignation est refusée par TypeError « cyclic reference ».
* Sérialisation et comparaison : `eq`, `%s`, `%q`, `%x` et `%j` déréférencent et opèrent sur la
  valeur courante. Une référence devenue invalide rend `null` en position imbriquée de `%s` et
  `<invalid reference>` dans la stringification racine, tandis que `%x`/`%j` propagent l'erreur
  de type. `%v` conserve le wrapper `Ref(...)` (référence invalide → `Ref(<invalid>)`), ce qui
  garde les structures cycliques rendables. `%t` rend `ref` (détails en §14).

8. Arithmétique
* integer = i64 (signé), float = f64.
* div entre deux integers retourne toujours un integer, avec troncature vers zéro (sémantique de division entière Rust/C). Donc div(10, 2) = 5 et div(7, 2) = 3. Une division avec au moins un float retourne un float.
* `sub` unaire effectue la négation. `div` unaire retourne le réciproque en Float ; `div(0)`
  produit DivisionByZero.
* mod : suit la sémantique C/C++ (troncature vers zéro, signe du résultat = signe du dividende) → mod(-7, 2) = -1.
* Division/modulo par zéro → DivisionByZero.
* Overflow sur add/sub/mul/pow/négation de i64::MIN → IntegerOverflow (arithmétique checked, jamais de wraparound silencieux).
* Mix integer/float dans une opération arithmétique → promotion automatique en float. string/bool/null en arithmétique → TypeError.
* Les opérations bitwise (`bit-and`, `bit-or`, `bit-xor`, `bit-not`, `bit-shl`, `bit-shr`)
  exigent des entiers. `bit-and`, `bit-or` et `bit-xor` sont des plis variadiques, avec
  identités respectives -1, 0 et 0. `bit-not`, `bit-shl` et `bit-shr` restent à arité fixe ;
  les décalages exigent un compte entre 0 et 63.

9. Coercions
Contexte	Règle
Arithmétique	int+int→int, float+float→float, int+float→float (promotion). div : int+int→int avec troncature vers zéro, sinon float. Autres types → TypeError.
eq/ne	Comparaison numérique cross-type autorisée (5 == 5.0 → t). Types non numériques différents → f (jamais d'erreur).
lt/gt/le/ge	Numérique uniquement, même règles de promotion que l'arithmétique. Types non numériques → TypeError.
$ (%s)	Accepte tout type, stringification canonique (les clés de struct ne sont pas entourées de guillemets).
$ (%d/%f)	%d exige un integer, %f accepte float ou integer (integer rendu exactement, sans promotion Float).
$ (%b/%h/%o)	Formats binaire, hexadécimal et octal ; `%8b`, `%16b`, `%32b` et `%64b`
		sont les formats binaires à largeur fixe.
$ (%j/%t/%v)	JSON, nom du type et représentation structurelle de debug.
Prédicats (if/loop/and/or/not)	Voir §1 truthiness.

10. eq par type
* Tableaux : égalité structurelle profonde, ordre compte.
* Structs : égalité structurelle profonde, ordre insignifiant (comparaison de map).
* Fonctions : égalité par identité (même closure physique), deux fn au code identique mais définis séparément → f.
* Floats : comparaison IEEE 754, sans epsilon : NaN n'est égal à aucune valeur (y compris NaN), les zéros signés sont égaux (`0.0 == -0.0`), et les infinis sont égaux à eux-mêmes.
* Références : déréférencées avant comparaison (§7). Une référence invalide contenue dans un
  composite rend la comparaison f, sans erreur : le composite ne peut être égal à aucune valeur.
* Variadique : `eq` est vrai seulement si tous les arguments sont égaux deux à deux
  (comparaison par paires, pas seulement adjacentes) ; `ne` est la négation exacte de `eq`,
  vrai dès qu'au moins une paire diffère. `(eq)` et `(eq x)` → t ; `(ne)` et `(ne x)` → f.
  Pour deux arguments, `ne` équivaut à `not eq`.

11. if / match
* if sans else, prédicat faux → retourne _.
* match : liste de paires prédicat expr. La première paire dont le prédicat est vrai détermine le résultat. t en tête de la dernière paire matche toujours → sert de vrai else :
(match (eq x 0) "zero" (eq x 1) "un" t "Default")
* Aucune paire ne matche et pas de t final → MatchError: no predicate matched (fail-fast plutôt que null silencieux).

12. loop / break / continue
* break a pour seule cible une loop. break valeur fait évaluer la loop entière à
  valeur ; break seul → _. Un break situé dans un match imbriqué dans une loop
  sort de la loop (le match est traversé, il n'est pas une cible de break). Hors
  de toute loop, break est une erreur BreakOutsideLoop, même à l'intérieur d'un
  match. Un break dans un match situé dans une fonction appelée depuis une loop ne
  sort que de la fonction (les boundaries de scopes de fn s'appliquent comme pour
  la profondeur de loop).
* continue : uniquement valide dans une loop. Hors d'une loop → ContinueOutsideLoop (même
  dans un match). Ne prend pas de valeur.

13. IO
* `io.open` reçoit une URI `file:` dont le paramètre de requête `mode` vaut `r`, `r+`, `w`,
  `w+`, `a` ou `a+`, puis retourne un descripteur entier. Les descripteurs 0, 1 et 2
  correspondent respectivement à stdin,
  stdout et stderr ; les fichiers ouverts reçoivent des descripteurs à partir de 3.
* `io.read fd` lit une ligne sans son retour à la ligne et retourne une string ; à EOF, retourne
  `_`. Les descripteurs non lisibles et invalides produisent IOError.
* Les lectures sont bufferisées et la mémoire tampon appartient au descripteur ouvert : les
  données pré-lues par un `io.read` restent disponibles pour l'appel suivant sur le même
  descripteur. `io.read` accepte les fins de ligne LF et CRLF (retirées comme une unité).
* Pour les modes mixtes (`r+`, `w+`, `a+`), lectures et écritures partagent le même fichier et
  la même position de flux ; une écriture se fait à la position courante, sauf `a+` qui écrit
  toujours à la fin du fichier. Un descripteur en écriture seule (`w`, `a`) n'est pas lisible ;
  un descripteur en lecture seule (`r`) n'est pas inscriptible.
* `io.write fd valeur` écrit une string et retourne le nombre d'octets écrits. Les descripteurs
  non inscriptibles et invalides produisent IOError.
* `io.close fd` ferme un descripteur et retourne `t` s'il était ouvert, sinon `f`.
* Les erreurs de système de fichiers et les entrées UTF-8 invalides produisent IOError.

13.1 HTTP
* Le module natif `http` expose `http.get`, `http.post`, `http.put`, `http.patch`,
  `http.delete` et `http.head`, chargés par `(use "http")`. `http.get url`, `http.head url` et
  `http.delete url` prennent une URL ; `http.post url body`, `http.put url body` et
  `http.patch url body` prennent une URL et un corps. Chaque appel effectue une requête HTTP
  synchrone de la méthode correspondante.
* Le corps est sérialisé en JSON à partir de la valeur Lisp : une string devient donc une
  string JSON (`"hello"`), tandis qu'un struct devient un objet JSON. Il est envoyé avec
  `Content-Type: application/json` ; l'argument correspondant est déclaré `"any"` dans
  `spec.type` car toute valeur sérialisable est acceptée.
* Une réponse `HEAD` retourne toujours une string vide. Pour les autres réponses, un
  `Content-Type` `application/json` (paramètres éventuels acceptés) ou tout type `+json`
  (suffixe de syntaxe structurée RFC 6839, comme `application/problem+json`) déclenche le
  décodage en valeur Lisp ; les autres types retournent le corps comme string.
* Les erreurs d'arité et de type de l'interface descripteur produisent ArityError et TypeError ;
  la sérialisation JSON du corps (valeurs non encodables comme les fonctions et les floats non
  finis) produit FormatError ; les erreurs d'URL, de transport, de statut HTTP 4xx/5xx, de
  lecture de réponse et de décodage JSON produisent HTTPError.

14. Interpolation $
* Syntaxe : `($ format arguments...)`. Le premier argument doit être une string ; les arguments
  suivants sont consommés dans l'ordre par les spécificateurs.
* `%s` accepte tout type et produit la stringification canonique. Les strings utilisées comme
  valeurs imbriquées dans les arrays et structs sont entourées de guillemets ; les clés de struct
  ne le sont pas. Les références sont déréférencées (§7) ; une référence invalide rend `null` en
  position imbriquée et `<invalid reference>` à la racine.
* `%q` exige une string et produit un littéral string Lisp entre guillemets, ré-utilisable par le
  lecteur : `"` → `\"`, `\` → `\\`, saut de ligne → `\n`, retour chariot → `\r`, tabulation →
  `\t` ; tout autre caractère est émis tel quel (le lecteur l'accepte verbatim). Le résultat
  re-parse comme la même string (`($ "%q" "hi\n")` → `"hi\n"`). Les références sont déréférencées.
* `%x` sérialise n'importe quelle valeur en source Lisp canonique, ré-utilisable par le lecteur :
  les strings imbriquées utilisent les règles d'échappement ci-dessus, les booléens deviennent
  `t`/`f`, `_` devient `_`, les floats utilisent leur représentation numérique (`NaN`, `Inf`,
  `-Inf` inclus), les arrays sont `[a b c]`, les structs `{clé:valeur ...}` dans l'ordre
  d'insertion. Les fonctions n'ont pas de représentation source et sont refusées. Le résultat
  re-parse comme une valeur égale à l'originale. Les références sont déréférencées (§7) ; une
  référence invalide propage une erreur de type.
* `%d` exige un integer et produit son écriture décimale signée.
* `%b` exige un integer et produit son écriture binaire sans largeur imposée.
* `%8b`, `%16b`, `%32b` et `%64b` exigent un integer et produisent une écriture binaire
  à largeur fixe. Les valeurs négatives utilisent leur représentation en complément à deux,
  tronquée à la largeur demandée.
* `%h` exige un integer et produit son écriture hexadécimale minuscule, sans préfixe `0x`.
  `%8h`, `%16h`, `%32h` et `%64h` produisent une écriture hexadécimale à largeur fixe de
  8, 16, 32 ou 64 bits (2, 4, 8 ou 16 chiffres) ; les valeurs négatives utilisent le
  complément à deux tronqué à la largeur demandée.
* `%o` exige un integer et produit son écriture octale, sans préfixe `0o`.
* `%f` accepte un integer ou un float. Un integer est rendu exactement en décimal (aucune
  conversion via Float, donc pas de perte de précision pour les grands entiers) ; un float est
  rendu via sa représentation numérique.
* `%j` accepte les valeurs sérialisables en JSON et produit une string JSON compacte ; les clés
  de struct sont des strings JSON entre guillemets :
  `_` devient `null`, `t`/`f` deviennent `true`/`false`, les structs ont des clés
  entourées de guillemets. Les fonctions ne sont pas sérialisables et les Float `NaN`,
  `Inf` et `-Inf` sont refusés. Les références sont déréférencées (§7) ; une référence invalide
  propage une erreur de type.
* `%t` accepte tout type et produit son nom de type (`null`, `bool`, `int`, `float`, `string`,
  `array`, `struct`, `function` ou `ref`).
* `%v` accepte tout type et produit sa représentation structurelle de debug (`Array(...)`,
  `Struct(...)`, `Int(...)`, etc.). Les clés de struct suivent la syntaxe Lisp (`name: value`),
  sans guillemets. Une référence apparaît comme `Ref(...)`, son contenu étant rendu en
  déréférençant l'emplacement (référence invalide → `Ref(<invalid>)`) : le wrapper est conservé —
  contrairement à `%s`/`%q`/`%x`/`%j` — pour que les structures contenant des cycles restent
  rendables.
* `%%` produit un caractère `%` littéral et ne consomme aucun argument.
* `%~` exige deux arguments : une string regex puis une string à matcher. La regex suit la
  forme `[options]~modèle` : les lettres d'options `g`, `m`, `i`, `s`, `x`, `U`, `u`, `R`
  écrites avant le `~` constituent le bloc d'options (qui remplace le défaut), le reste est le
  motif. Sans bloc, les options par défaut sont `gmu`. Correspondances : `g` = trouver toutes
  les correspondances (défaut ; sans `g`, seule la première est cherchée), `m` = ancres de
  ligne, `i` = insensible à la casse, `s` = le point matche les sauts de ligne, `x` =
  espacement et commentaires ignorés, `U` = gourmandise inversée, `u` = unicode, `R` = fins de
  ligne CRLF. Une regex invalide produit InvalidRegex ; un argument non-string produit
  FormatTypeError. `%~` calcule la liste des correspondances (de gauche à droite,
  sans chevauchement) mais n'émet rien par lui-même.
* `%M.C` émet la capture `C` de la M-ième correspondance : `C = 1` = correspondance complète,
  `C = 2` = premier groupe capturant, etc. `%N` est un raccourci pour `%1.N` : `%1` =
  correspondance complète de la première correspondance, `%2` = premier groupe capturant, etc.
  Ces sélecteurs ne consomment aucun
  argument. Aucune correspondance → `f` ; groupe optionnel non correspondant → `_` ; sélecteur
  sans `%~` précédent, index nul (`%0` ou `.0`), ou index de correspondance/capture hors
  bornes → FormatError.
* Un motif commençant par des lettres d'options suivies de `~` serait interprété comme un bloc
  d'options (limitation connue, sans échappement).
* Un `%` final, un spécificateur inconnu ou une largeur binaire autre que 8, 16, 32 ou 64
  produit une FormatError.
* Le nombre de spécificateurs consommant un argument doit correspondre exactement au nombre
  d'arguments restants → `FormatArityError` sinon.
* Un type incompatible avec `%d`, `%b`, `%h`, `%o`, `%f` ou `%j` produit une `FormatError`
  avec un sous-message `FormatTypeError`.
* Le résultat de `$` est toujours une string.

15. Regex
* La correspondance regex s'utilise uniquement via l'interpolation `$` : le spécificateur `%~`
  (§14) applique une regex à une string et calcule la liste des correspondances ; les
  sélecteurs `%M.C` et `%N` émettent la correspondance complète et les groupes capturants.
* Les regex utilisent le moteur Rust `regex` et opèrent sur des strings UTF-8. Pour chaque
  correspondance, la cellule 1 est la correspondance complète et les groupes capturants suivent
  dans leur ordre : cellule 2 = premier groupe, cellule 3 = deuxième, etc.
* Les regex opèrent sur des valeurs scalaires Unicode, pas sur des graphèmes : une correspondance
  ou une capture peut commencer ou finir au milieu d'un graphème. Par exemple, sur `"👍🏽"` (base
  emoji + modificateur de teint, deux scalaires), le groupe `(.)` capture la base (`👍`), alors
  que l'indexation d'une string (§1) retournerait le graphème complet. L'option `u` (défaut)
  conserve ce comportement scalaire.
* Un groupe optionnel non correspondant produit `_` ; une string sans aucune correspondance
  produit `f` pour tout sélecteur.
* Une regex invalide produit InvalidRegex avec le diagnostic du moteur ; un argument non-string
  produit FormatTypeError (§14).

16. Eval
* Syntaxe : `(eval source)` → évalue `source` comme du code Lisp et retourne la valeur de la
  dernière forme. `source` doit être une string ; sinon TypeError.
* La string est lexée et parsée comme un programme (§3), puis chaque forme est évaluée dans
  l'environnement courant de l'appelant : les liaisons visibles sont accessibles, et `let`, `set`
  et `use` restent valides dans le code évalué. Une string vide retourne `_`.
* Le code évalué hérite de la profondeur de boucle/match de l'appelant : `break` et `continue`
  s'y propagent vers la boucle englobante, comme pour du code au même niveau.
* `(eval "x")` évalue l'expression `x` (typiquement une variable) ; `(eval "(add 1 2)")` évalue
  du code en ligne ; une variable contenant du code source s'utilise de la même façon.
* Les erreurs de parsing et d'exécution internes sont propagées normalement ; leur diagnostic
  pointe sur l'appel `(eval ...)` du programme hôte.

17. Erreurs
Catégories : ParseError, NameError, TypeError, ArityError, MathError (div/0, overflow), IOError,
HTTPError, FormatError, InvalidRegex, DuplicateKeyError, DuplicateBindingError, MatchError, ContinueOutsideLoop,
BreakOutsideLoop, Interrupted et Quit.
Les erreurs de formatage conservent les sous-messages `FormatArityError` et `FormatTypeError`.
Pas de try/catch dans la spec → fail-fast : la première erreur stoppe le programme, message sur stderr, exit code non nul.
Les erreurs de parsing et d'exécution affichent le fichier, la ligne, la colonne, la ligne source
et un curseur `^`. Les erreurs qui traversent des fonctions utilisateur affichent aussi une trace
d'appel avec le nom de chaque fonction, ou `<anonymous function>`.
Sur Unix, Ctrl-C est converti en `Interrupted` et pointe vers l'expression en cours d'évaluation.

18. Structs, détails
* Ordre d'insertion préservé.
* Clés dupliquées à la construction → DuplicateKeyError (pas de "dernier gagne" silencieux).
* Clés identifiants uniquement, sans guillemets.
* En position opérateur d'un appel, seul un descripteur complet (`_` + `spec`) est appelable :
  l'appel déroule la valeur de `_` (validée appelable) en exactement un niveau (détails en §2).
  Les autres évaluations, notamment l'accès de champ et l'interpolation, conservent le struct
  complet.

19. Implémentation
Interpréteur tree-walking en Rust (parse → AST → eval récursif).

20. REPL intégré
* `(repl)` est une forme spéciale qui suspend le programme à l'endroit exact de l'appel et ouvre
  une session interactive : chaque ligne est évaluée comme un programme Lisp dans un scope
  enfant jetable, avec les mêmes profondeurs loop/match que l'appel.
* `(repl "label")` donne un nom à la session. L'invite est contextuelle : `repl> ` à la racine
  sans contexte, sinon `fichier:ligne> ` (ou `label@fichier:ligne> ` avec un label), où la ligne
  est celle du point d'exécution (le `(repl)` courant) dans la source réelle du programme — même
  si une ligne de shebang a été retirée avant l'analyse.
* Lignes : tout ce qui ne commence pas par `:` est évalué ; le résultat de la dernière forme
  (s'il n'est pas `_`) est affiché sur stdout au format lisp.
* Commandes (`:` en tête) : `:c`/`:continue` reprend le programme, `:q`/`:quit` l'abandonne
  (erreur `Quit`, seul cas où la session stoppe le programme), `:h`/`:help` liste les commandes.
  EOF sur l'entrée quitte la session comme `:c`. Comme dans l'évaluateur, `:c`/`:q`/`:h`
  n'acceptent pas d'argument (un argument → « commande inconnue »).
* Débogage : `:l`/`:list [N]` affiche les lignes autour du point d'exécution dans sa source
  (défaut ±3, `:l N` règle la fenêtre, `:l 0` = ligne courante seulement), en-tête
  `@ fichier:ligne (execution point)` et ligne courante marquée `>`. `:i`/`:inspect` liste les
  liaisons effectives : chaque nom une fois (le plus interne gagne), ordre alphabétique,
  valeur tronquée, `*` si le nom a aussi une liaison externe (ombragée), en-tête « N bindings
  across M scopes » ; `:i nom` affiche la valeur complète, le type, le scope de liaison
  (session/englobant/externe), la chaîne d'ombrage (liaisons externes successives, les plus
  internes d'abord) et, pour une fonction, `def: fichier:ligne` quand sa source est résolvable
  (sinon « defined in this session (repl) »). `:bt`/`:backtrace` affiche la pile d'appels
  vivante, cadre le plus interne d'abord, sous la forme `nom at fichier:ligne:col (texte)`;
  vide si `(repl)` est au niveau top-level.
* Pistes de source : la source en cours d'évaluation (fichier du programme, `(eval …)`, chaque
  ligne de session) est enregistrée avec son étiquette, son texte et le décalage de lignes éventuel
  (shebang), ce qui permet à `:l`/`:i`/`:bt` de résoudre les positions ; les fonctions définies
  dans la session sont signalées comme telles.
* Scope enfant : `let` ne lie que dans la session (aucune trace après `:c`) ; `set` et les
  lectures atteignent l'état vivant du programme. Les erreurs d'une ligne sont affichées
  (fichier `<repl>`, ligne 1, colonne pointée) et la session continue : elles ne se propagent
  jamais au programme. `(break)`/`(continue)` tapés dans la session se propagent et agissent
  sur la boucle englobante. Un `(repl)` imbriqué fonctionne (récursif) et son `:q` abandonne
  tout le run.
* La session lit et écrit sur le terminal de contrôle du processus (`/dev/tty`) : le stdin du
  programme n'est jamais consommé par la session, même quand le programme est chargé depuis
  stdin (`cat prog.lisp | small-lisp`) ; `io.read 0` continue de lire le stdin d'origine. Sans
  terminal de contrôle, `(repl)` échoue avec IOError — pas de repli silencieux sur stdin.
* Ctrl-C pendant une session : la ligne en cours est annulée, un message
  « repl: interrupted (:c continues, :q quits) » est affiché et la session continue. L'état
  Ctrl-C antérieur à la session est restauré à la sortie : un Ctrl-C après `:c` abandonne donc
  toujours le run comme avant. Hors session, Ctrl-C continue d'abandonner le run (`Interrupted`).
